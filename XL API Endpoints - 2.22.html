Overview

The XL API is a REST-based interface that enables you to directly integrate XL with other systems and applications, as well as get information in and out of XL devices. The XL API is available on XL devices with software versions 2.0 and later. The documentation on this page has been written for an experienced software developer.

The XL API is particularly useful for larger companies with well-staffed IT departments that want total control over the integration. For companies that lack these resources we recommend working with Vorne Integration Partners. Our Integration Partners provide a combination of turnkey software products and services (often built using API connections) and will help you to closely integrate XL with your existing systems, so that you don't need to dedicate resources to the maintenance of an API connection.

The XL API can be used to push information into the XL Devices. Here are five common uses of this functionality:

  • Push Part and Job settings into XL (and start a new Part Run).
  • Push a command into XL to manually start a Shift (with an existing Shift ID).
  • Push a Team name and Team size into XL (and assign these settings to the current Shift).
  • Push a command into XL to force it into a different production state and associated reason (e.g. Not Scheduled > No Production).
  • Push a unique message onto the LED scoreboard for a maximum of 30 seconds (e.g. "Great Job Team!").

The XL API can also be used to pull information from XL for use in another system (normally by writing to a database). Here are three common uses of this functionality:

  • Pull all data and settings from XL (for use as a device backup).
  • Pull all the metrics associated with a data channel (e.g. Hour, Shift, Production Day, Month, Part) into an SQL database for use with a third-party reporting platform.
  • Pull the currently active XL production state and reason (to trigger an event in a CMMS or ERP system).

Updates

As we continue to develop and add features to XL, the XL API will be subject to change. We might modify the API by adding new endpoints, removing existing endpoints, or making modifications to existing endpoints. The Release Notes section details all endpoint modifications by software release version. If you have any questions about how the API has changed, please feel free to contact us at support@vorne.com.

The content on this page was last updated in January 2026.

Querying the XL API

Each XL device is a standalone hardware-based system with an IP address on your Local Area Network. Each XL device has its own API interface that is accessed using its IP address. For example:

  1. To obtain Process State Reasons for an XL device at IP address 192.0.2.1
  2. The API string is: http://192.0.2.1/api/v0/dimensions/process_state_reason

There is no single URL provided by Vorne that can access the XL API for multiple devices. If you had ten XL devices, you would query each device individually (changing the IP address each time as appropriate).

Request and Response Details

The XL API uses the standard JSON data interchange syntax where:

  • Data is organized in name/value pairs separated by commas in which names and values in the form of a strings are in double-quotes.
  • Curly braces are used to contain objects and square brackets are used to contain arrays.

Note: Special consideration should be made for data with string values containing backslashes or double-quotes. These characters must be properly escaped using a preceding backslash.

  • Use \\ for a backslash.
  • Use \" for a double-quote.

Most responses detailed in this document will use the following JSON response envelope (there are two exceptions – the Device Versions and Scoreboard Graphic Overlay Image endpoints).

JSON Response (Envelope)
{
"data": {
...
},
"meta": {
...
}
}

The meta object includes the following fields:

FieldDescription
asset_id A 16-byte UUID (Universally Unique Identifier) that uniquely identifies the production asset responding to the API request.
data_version Data Version as described in the Device Versions endpoint.
device_id The Ethernet MAC address of the hardware device responding to the API request.

Every request returns an HTTP response status code. A successful request will return a status code of 200.

An unsuccessful request will return a status code in one of the following classes:

  • 5xx for a server error.
  • 4xx for a client error.

For client errors the following error object will be included in the meta object:

FieldDescription
detail A human-readable explanation specific to this occurrence of the problem.
status The HTTP status code applicable to this problem, expressed as a string value.

For example, the complete response related to a 404 HTTP response may look like:

Example Failure Response
{
"meta": {
"asset_id": "03b93b6b-cb7f-43e7-af2d-1c47483b82ad",
"data_version": "1.0",
"device_id": "08:00:27:73:7E:4F",
"error": {
"detail": "Not found: bad_key",
"status": "Not Found"
}
},
"data": {}
}

Device Status Endpoints

Device status endpoints provide general information about the status of the Vorne XL device.

Device Versions

The response to the GET request returns the firmware version currently installed on the Vorne XL device, the corresponding data version, and other information about the Vorne XL device.

The URL for this endpoint is atypical and DOES NOT include the standard JSON envelope. This provides a backward compatible mechanism to determine what generation of Vorne XL device is responding to the request.

GET Request GET rest/cpe/attributes
Response {
"asset_name": "XL810-1",
"data_version": "1.2",
"device_model": "xl810_32080t",
"locale": "en-US",
"location": "Plant",
"origin": "xlpa",
"originName": "XL810-1",
"product_variant": "Gold",
"version": "2.10.1.0"
}

The data version attribute (data_version) provides an indication of what data model is being employed by the XL device. This attribute follows the precepts of semantic versioning, but omits the patch number. Specifically, the data version takes the form X.Y where X and Y are non-negative integers, and does not contain leading zeroes. X is the major version, Y is the minor version. Each element increases numerically (e.g. 1.9 → 1.10 → 1.11).

For Major Version X, when an XL software package with a given data version has been released, the data model content of that data version will not be modified. Any modifications to the data model will be released as a new data version. Major version X will also be incremented when any backwards incompatible changes are made to the data model. Backwards incompatible changes include:

  • Removing tables or channels
  • Removing non-derived columns or fields

Minor version Y will be reset to 0 when major version X is incremented (e.g. 2.6 → 3.0) or incremented when new backwards compatible changes are made to the data model. Backwards compatible changes include:

  • Adding new tables or channels
  • Adding non-derived columns or fields
  • Adding derived columns or fields
  • Removing derived columns or fields
  • Changing the formula of a derived column or field

Data version 1.0 defines the data model as released in XL software release 2.9.0. The way in which the data version number is incremented after this release is dependent on how the data model changes.

Table Records

The response to the GET request returns a list of table events in a particular table. Using string parameters, the events can be aggregated or limited to show a subset of their actual fields. The results are returned within an array (which may be empty due to filters), and the events are provided as arrays. If fields were specified, the events will respect that order. Otherwise we return every field and expect the caller to know the order. Query string parameters include:

ParameterRequiredDescription
fieldsNoA list of fields to retrieve (e.g., fields=event_id,good_count).
groupNoA field to aggregate and return results by (e.g., group=shift_event_id). To aggregate all the events into a single event, use the special value "none" (e.g. group=none).
limitNoDo not return more than this many separate events (e.g., limit=5).
sortNoSort (ascending or descending) by a certain field (e.g., sort=event_id). To sort in descending order, prepend a minus sign to the sort value (e.g. sort=-event_id).

Additional query string parameters can be specified to filter by certain fields. For example, to get events on Production Day "16934", the query string parameter would be: production_day_number=16934

Filters can also include logical operators: "lt", "gt", "lte", "gte", "eq", and "neq" (e.g. event_id[neq]=9)

An easy way to know if category values have changed is to denormalize the main tables to also include the display names. This can also be achieved by providing a single endpoint where the most recent Record ID and Modification ID for every table is provided.

Events

Using string parameters, the events can be aggregated or limited to show a subset of their actual fields. The response to the GET request returns a list of channel events for a particular channel. The results are returned within an array (which may be empty due to filters), and the events themselves are provided as arrays. Query string parameters include:

ParameterRequiredDescription
fieldsYesA list of fields to retrieve (e.g., fields=event_id,good_count).
groupNoA field to aggregate and return results by (e.g., group=shift_event_id). To aggregate all the events into a single event, use the special value "none" (e.g. group=none).
limitNoDo not return more than this many separate events (e.g., limit=5).
offsetNoDetermine where to start the list of events (e.g., offset=2). This is often used in combination with limit (e.g., limit=5,offset=2 will return the 3rd through 7th events).
sortNoSort (ascending or descending) by a certain field (e.g., sort=event_id). To sort in descending order, prepend a minus sign to the sort value (e.g. sort=-event_id).
chronologicalNoIf enabled (e.g., chronological=true), then events that were interrupted by another event will be shown as multiple event portions.
includeNoOnly supports the value include=comments.

Additional query string parameters can be specified to filter by certain fields. For example, to get events on Production Day "16934", the query string parameter would be: production_day_number=16934

Include Comments

Adding the include=comments parameter to any events query will include all comments associated with the returned events in the following format:

{
"attributes": {
"content": String, // The body text of the comment
"created": String, // The ISO8601 timestamp the comment was created
"production_day_number": Number, // The production day number the event the comment was made on takes place
"slice_offset": Number, // Presently not utilized, always 0.
"slice_order": Number // The first slice_order value of the event this comment was made on
},
"id": String, // The unique identifier of the comment
"links": {
"self": String // A URL which can be used to look at this specific comment via the dedicated comments API
},
"relationships": {
"target": {
"data": {
"type": String, // The type of the event the comment was made on (e.g. shift, part, job)
"id": String // The event_id for the event the given type the comment was made on
}
}
},
"type": "comments"
}

This endpoint is effectively the same as adding a filter for the channels current event_id to the request and therefore is not compatible with filters that restrict the time range of the query. This REQUIRES a fields parameter described above or an error is returned. The response to the GET request returns the data for the current event.

Previous Event

Manufacturing Process Endpoints

Manufacturing Process Endpoints provide the ability to query and manipulate the manufacturing process as understood by the Vorne XL device. For instance, they can be used to start a new job or enable a lunch break.

Start Part Run (Job)

Starting a new part run also disables all Not Scheduled production states. This will result in the device returning to automatic run/down detection.

In HTTP response start_with_changeover, changeover_reason, changeover_target, and disable_when will only be present if start_with_changeover is true. Using setting disable_when can either be an array of rule objects or just a single rule object. When using an array it handles these rules as a logical OR, so for example you could have it disable based on changeover_target_time or it's gone into definitely running. These rules determine when the changeover reason will be disabled:

  • {} to have it disable when scanning a barcode only
  • { "type": "timer" } to have it disable changeover once changeover_target time has elapsed or scanning a barcode
  • { "type": "metric", "channel": "production_metric", "metric": "run_confidence", "at_least": 1.0 } to have it disable changeover when it's gone into definitely running or scanning a barcode

Controlling a part run:

  • To end a part run, set part_id to "null".
  • If a Part already exists in XL configuration, the part_id value can be either the Part ID or (added in 2.11) the Alternate Part ID.

Note: part_description and job_description is stored in live memory only, for display on the LED scoreboard at the start of a new Part or Job. These values are not stored in historical memory and are not available in the XL Web Page Interface for use in any reports.

Expected Count Per Cycle and Utilized Count Per Cycle are only set/appear based on Include Count Factor in OEE Performance.

Enable Process State (Production State)

Expanded in 2.20. This end point allows you to get a list of active process state reasons.

Expanded in 2.12. This end point allows the API to:

  • Activate a production state with an associated reason.
  • Change the reason associated to a down event.

Production states (formerly referred to as process states) are organized in a hierarchy. Down, Running, Running Slow, Running Poor Quality, and Running Poorly are the five lowest priority levels of the hierarchy and are the only production states that are mutually exclusive. All other production states are prioritized based on their level in the hierarchy, with higher production states overriding lower production states. When a higher production state is enabled, the lower production state remains enabled and will become active again once the higher production state condition ends. For more information on production states, refer to the Meet XL guide.

XL can alternate between Run and Down automatically, using the run detector (default). Automatic run detection can also be disabled, allowing the user to manually control Run/Down detection.

When XL is automatically detecting Run/Down:

  1. The Run and Down states cannot be enabled through the API.
  2. This endpoint can enable other production states (not Run or Down) by enabling an associated reason.
  3. This endpoint can assign a down reason to a currently active down event, or change the down reason associated to the last down event (if XL is not currently down).

When XL Run/Down detection is manually controlled:

  1. This endpoint can be used to alternate between Run and Down, and to enable other production states.
  2. The “running” reason enables the Run production state with a reason of “Running Normally”. The Run Variants (Running Slow, Running Poor Quality, Running Poorly) are not available.
  3. The “running” reason infers that the process is Definitely Running since the production state is being explicitly provided. For example, if a changeover is configured to end by Definitely Running, when the Running production state is active the changeover will end.
  4. The “down” reason enables the Down production state, with the default reason of “Down”. It is the only down reason that sets XL to the down production state.
  5. To set XL to Down with a different reason, XL needs to be sent two strings: A string to activate “down” (which assigns the default reason of “Down”), and a second string to assign a different down reason.

To manually control Run/Down detection, disable automatic run detection by un-checking the Enable Automatic Run Detection option located on the Settings > Parts and Run States > Run States page. If automatic run detection is active then requests to manually enable Run or Down will fail.

The following points apply irrespective of the Run/Down detection setting:

  1. All production states that are not Run or Down can be enabled through the API by sending a string to enable an associated Reason (e.g. the No Production state can be enabled by sending a string to enable the No Orders reason). Note that when a production state with a higher priority than an active state is enabled, the active production state is paused. The new state will remain active until either:
    1. The End Event condition for the reason (defined on Settings > Reasons page) is met, at which time the new state ends and XL reverts to the highest enabled production state below this state in the hierarchy.
    2. Start Production is activated, which disables all active production states and reverts to either run or down.
    3. A higher priority production state is enabled, at which time this event is paused.
  2. If a down reason is enabled and XL is Down, the reason will be assigned to the current down event.
  3. If a down reason is enableded and XL is not Down, the reason will be applied to the last down event (changing the reason currently assigned to that event).
  4. To slice a single down occurrence into multiple down reasons, refer to the Split Down Event endpoint.
  5. When any reason that is not a down reason is activated, the reason activates or re-activates the associated production state as per the hierarchy rules described above. Down is the only Production State that supports Split Down Events.

The response to the POST request returns the details of a specific production state. The POST request tags or enables a production state (process state in the API).

Inject Logical Inputs

Added in 2.11. The inputs endpoint provides the ability to send inputs via the API (similar to the Bench Test page in the WPI). The POST request injects a certain number of logical inputs on a single pin based on the payload provided. If the "count" attribute is absent from the payload the request will inject a single logical input. Logical inputs are not affected by debouncing, prescaler, or inhibit settings, though they are affected by count multipliers assigned to a part. The request will fail if the ability to inject inputs via the API has not been enabled via the Digital Inputs configuration in the WPI. The response to the POST request returns no data.

POST Request POST api/v0/inputs/:input_pin_number
{
"count": 10
}
Response {}

Data Management Endpoints

Data Management Endpoints provide the ability to alter the stored data on the device. Currently, only the Replace Device ability is supported.

Replace Device

Added in 2.16. Request that all data is erased and new data starts with specified ID values.

The Replace Device endpoint is intended to be used in conjunction with an external Data Collector when an XL device needs to be replaced. It properly prepares the replacement device so data collection can continue seamlessly without record conflicts. All existing configuration and data will be cleared from the replacement device.

The request contains the highest identifier values that are present in previously collected table records. All future events will use higher identifier values to ensure there are no collisions. If there are no values previously collected for a table, 0 (zero) should be used for all required identifiers for that table.
